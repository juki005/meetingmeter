# 2. Technical Objective

Implement MeetingMeter as an authenticated application in which a meeting organizer can:

1. configure a meeting;
2. select people and Guests to measure;
3. explicitly start measurement;
4. observe elapsed time and estimated cost in real time;
5. pause, resume, or mark participants as left;
6. explicitly end the meeting;
7. obtain an immutable final result;
8. retain the result in private history;
9. export the result as PDF, Image, and CSV.

The implementation must preserve the approved semantics:

- measurement begins only after explicit Start;
- participant measurement is independent;
- PAUSED stops measurement but keeps the participant in the meeting;
- LEFT ends measurement for that participant;
- unknown cost is not zero;
- only known cost contributes to the calculated estimated total;
- completed meetings do not continue accumulating;
- final results are stable;
- meeting/history data is private to the owner unless future approved authorization rules explicitly change this;
- cost is always presented as an estimate, not accounting/payroll/billing/payment data.

# 3. Proposed Architecture

## 3.1 Application architecture

Use a conventional web application with:

- responsive client UI;
- authenticated application/API layer;
- relational persistent database;
- server-authoritative meeting state;
- deterministic cost calculation;
- export generation;
- explicit authorization at every protected resource boundary.

The architecture should avoid treating the browser clock as the source of truth for accumulated meeting cost.

### Authority model

The server/database is authoritative for:

- meeting state;
- participant state;
- measurement start/stop timestamps;
- measured participation intervals;
- hourly rate values used by a meeting;
- calculated accumulated cost;
- meeting completion;
- final result.

The client is responsible for:

- rendering;
- user interaction;
- live display updates between authoritative state refreshes;
- responsive behavior.

---

# 4. Measurement Model

The core technical model is interval-based rather than counter-based.

For each measured participant, maintain measurement intervals.

Conceptually:

`ACTIVE → interval starts`

`PAUSED → interval closes`

`RESUMED → new interval starts`

`LEFT → active interval closes and participant measurement terminates`

`MEETING END → all remaining active intervals close`

Measured participation time is the sum of completed measurement intervals.

This avoids accumulating financial values through repeated client-side increments.

---

# 5. Cost Calculation

For a participant with a known hourly rate:

`participant_cost = hourly_rate × measured_seconds / 3600`

Meeting estimated cost:

`meeting_cost = sum(known participant costs)`

Unknown-rate participants:

- remain explicitly unknown;
- have no numeric participant cost;
- contribute no numeric amount to the calculated total;
- must not be represented as having a rate of zero.

The final result must retain enough information to distinguish:

- known calculated cost;
- unknown cost information;
- participants for whom cost could not be calculated.

The UI must continue to describe the numerical result as an estimate.

---

# 6. Rate Snapshot

When a person is added to a meeting and becomes part of measurement, the technical implementation should store the hourly-rate value used for that meeting.

This prevents historical meeting results from changing merely because a person's profile rate is edited later.

The meeting record therefore represents the historical calculation context.

For a Guest:

- known rate → store the supplied meeting rate;
- unknown rate → store an explicit unknown state.

This is an implementation requirement derived from the Product requirement that completed results remain stable.

---

# 7. Meeting State Model

Recommended persisted meeting states:

- `CONFIGURED`
- `LIVE`
- `ENDED`

Participant measurement states:

- `ACTIVE`
- `PAUSED`
- `LEFT`

`RESUMED` is a transition back into `ACTIVE`, not a separate persisted terminal state unless implementation requires an audit/event representation.

### Valid transitions

Meeting:

`CONFIGURED → LIVE`

`LIVE → ENDED`

Participant:

`ACTIVE → PAUSED`

`PAUSED → ACTIVE`

`ACTIVE → LEFT`

When the meeting ends:

`ACTIVE → measurement stopped`

Participants already `PAUSED` or `LEFT` retain their respective final states.

No transition from `ENDED` back to `LIVE`.

# 9. Historical Immutability

After `MEETING → ENDED`:

- no further measurement accumulation;
- participant measurement intervals cannot continue;
- final calculated result cannot drift because of later profile-rate changes;
- completed meeting data remains available in history;
- exports operate against the stored final result.

Any correction workflow for completed meetings is outside the approved MVP and must not be introduced implicitly.

---

# 10. Authentication and Authorization

Authentication is required.

Minimum authorization model:

- authenticated users can access their own account/profile;
- users can manage their own people;
- users can access meetings they own;
- users can access their own meeting history;
- users cannot automatically access another user's private meetings/history;
- participant hourly-rate information must not become globally readable merely because the participant exists.

Every protected API operation must enforce ownership/authorization server-side.

Client-side route protection alone is insufficient.

# 12. Concurrency and Idempotency

Start, participant state changes, and End are state transitions and must be protected against duplicate requests.

Examples:

- two Start requests must not create two measurement starts;
- repeated Pause must not create overlapping/duplicate intervals;
- repeated Resume must not create multiple active intervals;
- repeated Leave must not alter an already-left participant;
- repeated End must not create a second finalization event or change the completed result.

The backend should use transactional state checks for these transitions.

---

# 13. Real-Time Meter

The live UI requires a continuously updating display.

The authoritative persisted state should be timestamp-based.

The client may update the displayed elapsed time/cost locally between server synchronizations, but must periodically reconcile against authoritative server state.

The implementation must not depend on a permanently running browser timer as the source of financial truth.

The exact real-time transport — polling, server-sent events, WebSocket, or equivalent — is an implementation decision. For the MVP, the simplest mechanism that reliably preserves live behavior and state correctness should be selected by AG.

This decision must be documented in the final technical implementation record.

# 19. Technical Risks

### R-01 — Timing accuracy
Incorrect interval handling could produce incorrect costs.

Mitigation: server-authoritative timestamps and interval calculations.

### R-02 — Duplicate state transitions
Repeated requests could corrupt measurement intervals.

Mitigation: transactional transition validation and idempotent mutation behavior.

### R-03 — Unknown cost semantics
Unknown Guest rates could accidentally become zero.

Mitigation: explicit known/unknown representation throughout data model, API, calculation, UI and exports.

### R-04 — Historical instability
Profile-rate changes could alter old meeting results.

Mitigation: meeting-level rate snapshot.

### R-05 — Unauthorized private data access
Meeting/history information is sensitive.

Mitigation: server-side ownership checks on every protected resource.

### R-06 — Export divergence
Exports could omit required receipt information.

Mitigation: export from the same finalized result model and verify against acceptance criteria.

### R-07 — Design mismatch
Implementation could diverge from the actual Stitch design.

Mitigation: mandatory Antigravity/Stitch verification gate before implementation.
